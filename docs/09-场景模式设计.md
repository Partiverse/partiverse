# 场景模式设计(Scene Modes)v1.0

> 状态:✅ v1.0(2026-10-08,基于库形态产品先例调研:Plex/Jellyfin/Infuse/MusicBee/Calibre/Koodo/Immich/DEVONthink/Eagle/Zotero/Notion/Obsidian/HA/Kodi/Figma/MCP Apps/Zed)
> 回答两个问题:①聚合后的资产以什么形态呈现(场景);②场景做成插件还是其他机制。

---

## 1. 核心结论

1. **场景 = 对统一资产索引(Node×Particle)的预置投影**,不是另一套浏览入口。同一窗口内切换:侧栏保留"文件"(文件浏览器主视图,永远兜底)+ 各场景库(照片馆/影视库/音乐厅/书房/文档库)。**所有先例(Plex/Eagle/DEVONthink/Notion/Immich)全部是同窗口切换,无一做成独立模式。**
2. **视图引擎必须内置;插件边界划在元数据/解析/预览/动作上**。调研中没有任何一个库形态产品把"场景视图本身"插件化;Kodi 的"皮肤改一切"是已被证伪的路线(版本升级即损坏、开发者弃坑)。Obsidian 式"核心内置+长尾插件"分层成立。
3. **真正的成本在元数据管线,不在布局**:海报墙/封面墙/时间线都只是投影;缩略图、EXIF/标签解析、刮削(+人工纠错闭环)、格式解析、人脸聚类、嵌入向量才是场景的护城河——而这套管线恰是 V2/V3 复用 partisync sidecar 管线(✅D21)的部分。
4. **兜底原则**(避免 Apple Photos iOS 18"回不去"式反弹):任何场景下用户都能退回文件视图找到同一文件;AI/语义能力永远是"即时确定性结果 + 异步增强",保留经典开关(Google Photos 被迫加回的教训)。

## 2. 场景框架抽象(内置引擎的 schema)

一个场景 = 一份声明式配置:

```
Scene {
  filter:    类型/来源/时间/标签规则(= 智能文件夹,保存的搜索)
  grouping:  人物/相册/专辑/艺人/作者/年份/合集/文件夹
  layout:    海报墙(2:3 卡) | 画廊 | 时间线 | 列表 | 表格
  card:      字段绑定(封面、进度条、评分、徽标)
  actions:   播放/阅读/预览/定位到文件视图/打开来源/外部打开
}
```

- 该 schema 同时服务三方:①内置官方场景(随版本发布);②**用户自定义智能视图**(把内部 schema 暴露成 UI——Eagle 智能文件夹/DEVONthink 智能群组/Notion 视图的公约数);③未来第三方场景包。
- 场景的卡片与详情模板允许"深度定制型布局"(海报墙不是通用表格能投影出来的),这既吸收 Notion 式投影机制的成熟,又不落"通用但平庸"(调研结论:媒体库产品无一采用纯通用投影)。

## 3. 各场景要点与管线依赖

| 场景 | 关键交互(先例共识) | 元数据管线 | 分期 |
|---|---|---|---|
| 照片馆 | 时间线/回忆;人物/地点;AI 搜索带经典开关(Immich 是气质最近的参照) | 缩略图、EXIF、人脸聚类、嵌入向量 | **V1**(管线最确定:缩略图+EXIF 即可用) |
| 文档库 | 列表+预览+全文/OCR 检索;智能文件夹;专业细分(文献引用)留给专门工具 | OCR、全文索引 | **V1** |
| 影视库 | 海报墙+合集;**刮削失败是体验核心:Identify 手动重匹配、NFO/本地图优先、元数据锁定(Plex/Jellyfin/Infuse 三家公约数)**;进度记忆免费、外挂字幕同名自动加载、清晰度无墙(08 规划 §6.4) | 刮削(TMDB)+纠错闭环;转写后置 | **V2**(管线最重) |
| 书房 | 封面墙+格式过滤(epub/pdf 同书目多格式)+阅读进度(Calibre 长期缺口=我们的机会) | 格式解析、封面提取、阅读进度 | **V2** |
| 音乐厅 | 专辑/艺人/流派分组视图(MusicBee 证明配置化即可);歌词后置 | 内嵌标签解析(刮削依赖最低) | **V2.5**(管线最轻,可提前) |
| 自定义智能视图 | 用户版场景编辑器(filter+grouping+layout) | 复用以上管线 | **V3**(schema 经五个内置场景验证后再暴露——吃自己狗粮) |
| 第三方场景包 | 声明式 schema + 可选 iframe 沙箱详情卡(**MCP Apps/SEP-1865 与 Figma showUI 模式,2026 已成标准**)+ WASM 无 UI 动作扩展(Zed 模式) | 第三方自备 | **V3+/M4 候选**;明确不做 Kodi 式自由画布 |

## 4. 机制裁定(回答"插件还是其他方式")

- **不是插件,是内置的"场景框架 + 场景即配置"**;第三方开放分两步:先向用户开放声明式自定义场景(V3,schema 稳定后),再向第三方开放"场景包"(声明 schema+沙箱详情卡+无 UI 动作,M4 候选)。
- 与 D22 插件体系的关系:ext-host(WASM)继续承载**动作类**扩展(工具/脚本/驱动);场景**视图**走声明式 schema + 宿主渲染,不走 WASM 画 UI——这是调研中所有成功先例的共同边界,也是体验一致性的保证。
- 失败教训入册:Kodi 皮肤生态崩坏(自由画布)、foobar2000 面板拼装门槛、Obsidian 社区插件弃维护、Jellyfin 无客户端插件致多端能力漂移(多端视图引擎必须同源)。
